---
title: "Status Codes"
description: "HTTP and transactional status codes returned by the Milele API."
---

Milele uses two layers of status codes:

- The **HTTP status code** indicates whether the request itself was valid.
- The **`status` field** in the JSON body describes where a transaction is in its lifecycle.

Use them together to decide whether to retry, show an error, or mark a payment as complete.

---

## HTTP status codes

| Code | Meaning |
|------|---------|
| `200` | OK |
| `400` | Bad Request |
| `401` | Unauthorized |
| `403` | Forbidden |
| `404` | Not Found |
| `409` | Conflict (e.g. duplicate request) |
| `429` | Too Many Requests — rate limit, or orders paused after repeated low-balance failures (`reason`: `INSUFFICIENT_BALANCE_BACKOFF`). Wait for `Retry-After`. |
| `500` `502` `503` `504` | Server error. The request may have reached the server. See [Handling statuses](#handling-statuses) before retrying. |

A low balance is not an HTTP error. The request returns `200` and the body's `status` is `7` (Insufficient funds).

---

## Transactional status codes

Returned in the `status` field of the response body on **payments, payouts, airtime, and bill** endpoints.

### Successful

| Code | Description |
|------|-------------|
| `20` | **Success** — transaction completed and funds moved |

### Pending

| Code | Description |
|------|-------------|
| `0` | **Created** — Milele accepted the request but has not yet submitted it to the provider |
| `3` | **Submitted** — request forwarded to provider, awaiting response |
| `31` | **Processing** — provider is still processing the request |
| `100` `101` | **Retrying** — Milele is automatically retrying with the provider |
| `202` | **Held** — paid, but delivery is paused; it is sent automatically when delivery resumes, or reversed (`8`) if it cannot resume |
| `203` | **Delivering** — a held transaction is being sent now |
| `204` | **Refunding** — a held transaction is being reversed; it ends as `8` |

Treat any code not listed on this page as pending: keep checking or wait for the webhook. Never resend it with a new idempotency key.

### Failed

| Code | Description |
|------|-------------|
| `1` | **Cancelled** — you or the customer cancelled before completion |
| `2` | **Failed** — generic failure from the provider |
| `5` | **Invalid** — parameters accepted but provider rejected them (e.g. bad account number) |
| `6` | **Timeout** — provider did not respond within the configured window |
| `7` | **Insufficient funds** — your Milele balance or the customer's balance is too low |
| `8` | **Reversed** — provider reversed the transaction after an earlier success |
| `9` | **Refunded** — you or Milele initiated a refund |
| `10` | **Forbidden** — business rules prevent this transaction |
| `11` `120` | **Rejected** — provider explicitly rejected the transaction |
| `13` `15` `16` `24` | **Error** — unexpected provider or internal error; treat as failed and investigate |
| `17` | **Duplicate** — a transaction with the same idempotency key was already processed |
| `18` | **Expired** — transaction expired before completion |
| `19` | **Inactive** — target account or service is inactive |

## Handling statuses

If a payout request times out or you lose the response, the payout may already exist. Within 24 hours of the original request, retry only with the unchanged body, including the same `idempotencyKey`. Sign it again with a fresh `X-Api-Timestamp`.

Once 24 hours have passed, do not retry a payout whose outcome is unknown. [Check the original payout by transaction ID](/core/status), check your [webhook records](/webhooks), or contact support.

<AccordionGroup>
  <Accordion title="Server or provider errors">
    For an endpoint that supports [idempotency](/prerequisites/idempotency), reuse the original body and key if you retry after HTTP `5xx` or a provider timeout or error (transaction status `6`, `13`, `15`, `16`, or `24`). For payouts, the 24-hour limit above applies.
  </Accordion>

  <Accordion title="Do not retry automatically">
    Do **not** automatically retry when:

    - HTTP status is `4xx` (`400`, `401`, `403`, `409`), or
    - Transactional status is `1`, `2`, `5`, `7`, `10`, `11`, `17`, `18`, `19`, or `120`.

    Show the error to the user. After HTTP `409`, confirm the original payout's status. Never use a new key to retry the same payout. See [Retry a payout safely](/payments/payouts#retry-a-payout-safely).
  </Accordion>
</AccordionGroup>

When retrying after `5xx` or `429`, use **exponential backoff** (e.g. wait 1s, then 2s, then 4s) and respect the `Retry-After` header on 429. See [Rate limiting](/prerequisites/rate-limiting) for details.

## Error responses

When a request fails, the body may use one of these shapes:

**Simple error string:** many endpoints return a JSON object with an `error` field:

```json
{ "error": "Too many requests" }
```

**Structured response:** some endpoints include a `status` and a human-readable field such as `message` from third party providers:

```json
{ "status": 400, "message": "missing_params" }
```

**Target shape (for new and updated endpoints):** a consistent error object may include `type`, `code`, `message`, and `request_id` to support machine-readable handling and support lookup:

```json
{
  "error": {
    "type": "invalid_request_error",
    "code": "missing_params",
    "message": "Your request is invalid.",
    "request_id": "req_abc123"
  }
}
```

Use the HTTP status code to detect failure; parse `error` or `message` (and optional `status`/`code`) to show or log a reason. When contacting support, include the `X-Request-Id` response header if present (see [Request ID for support](#request-id-for-support) below).

### Request ID for support

Every API response includes an **`X-Request-Id`** header with a unique value for that request. If you contact Milele support about an error or unexpected behaviour, include this value so we can look up the request in our logs.
